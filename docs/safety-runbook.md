# 安全 runbook

異常情況的逐步處置。每一節說明：**你會看到什麼**、**軟體已自動做了什麼**、
**你必須做什麼**。

> **共同前提**
> - 本軟體**不取代券商端人工確認**。任何委託／成交／持倉存疑時，仍須依元大規定
>   向營業員或櫃台確認。
> - UI **沒有**人工重新查詢或人工同步持倉的按鈕（刻意設計）。
> - 目前版本**沒有**「安全暫停 → 恢復」的操作流程。要停止自動交易的唯一方式是
>   **登出**或**關閉程式**。要出清部位用**緊急平倉**。
> - 風控平倉（04:55 強制平倉、300 點停損、獲利回吐 30%）**不會**被任何進場禁令阻擋。

---

## 1. 部分成交（平倉或進場）

**你會看到**：交易活動區顯示某委託部分成交、仍有剩餘量；活動委託未消失。

**軟體已自動**：
- 以**實際剩餘部位**維持風控（停損／獲利回吐基準不變）。
- 該契約有活動委託時，策略引擎不會送出新的進場、加碼或另一張平倉單。

**你必須**：
1. 等待該委託成交完成或失效。
2. 若長時間未完成（逾時），視同「未成交逾時」處理（見第 3 節）。
3. 平倉部分成交且已接近 04:55：用「緊急平倉」對剩餘部位重新查詢並確認平倉，
   必要時向券商確認實際部位。

## 2. 拒單

**你會看到**：日誌出現委託遭拒（reject）事件；交易活動區該委託標示失敗。

**軟體已自動**：
- 不會自動重送。
- 不會因此反手。

**你必須**：
1. 查看日誌中的拒單原因（correlation ID 一併記下，見[除錯日誌](debug-logging.md)）。
2. 若為平倉遭拒且仍有部位：用「緊急平倉」重新查詢並確認，必要時向券商人工下單平倉。
3. 若為進場遭拒：通常可忽略；確認目前無非預期部位即可。

## 3. 未成交逾時 / 委託狀態不明（Unknown）

**你會看到**：某委託長時間停留在送出中／未回報，或日誌出現 `UNKNOWN` 狀態。

**軟體已自動**：
- **絕不自動重送狀態不明的委託**（全域安全規則）。每張委託都有冪等識別碼。
- 該契約有此類委託時，不送出任何新委託。
- 重新啟動時的復原程序（`RecoveryCoordinator`）會查詢券商實況，任何未解決的委託
  或未知的券商委託都會讓復原結果為 `PAUSED`，不建立新的持倉基準。

**你必須**：
1. **向元大營業員／櫃台確認該委託的真實狀態與成交結果。**
2. 依券商告知的真實狀態，決定是否需要人工平倉或調整。
3. 確認一致後再重新啟動程式，讓復原程序重新查得乾淨狀態。

## 4. 斷線 / 重連

**你會看到**：登入狀態轉為未連線；行情圖狀態列顯示斷線或 stale；日誌出現
`connectivity_channel_health_changed`、`ChannelHealthChanged`。

**軟體已自動**：
- 連線監控（`ConnectivityMonitor`）記錄通道健康變化並嘗試重連（backoff）。
- 重連成功後（`BrokerSessionReady`）自動觸發持倉／委託／成交的重新核對 fan-out。
- 行情斷線期間的 K 棒**缺口予以保留、不補值**；資料 stale／有缺口時策略維持 blocked。

**你必須**：
1. 確認網路與 VPN／防火牆對元大主機（見[安裝手冊第 2 節](installation-manual.md)）的連線。
2. 等待自動重連。若長時間無法重連：登出並關閉程式，排除網路問題後重開，
   讓復原程序重新查得實況。
3. 斷線期間若跨越了 04:55：見第 6 節。

## 5. 自動持倉核對異常（含手機 App 或其他來源造成的異動）

**你會看到**：「自動持倉核對」區顯示差異說明，例如
`MXF:YYYYMM:expected=1:actual=0`；或顯示查詢失敗。日誌出現
`reconciliation_mismatch_detected` 或 `position_query_failed`。

**軟體已自動**：
- 偵測到差異或查詢失敗時，發出 `PositionDiscrepancyDetected`，策略引擎**擋下該契約
  的所有新進場與加碼**（風控平倉不受影響）。
- **不會**自動覆寫本機的預期部位基準。
- 差異在下次自動核對重新確認一致（`ManualPositionSyncCompleted`）後自動解除封鎖。

**你必須**：
1. 釐清差異來源：是否曾用**手機 App／網頁／營業員**對同一帳戶下單或平倉？是否有
   **其他契約月份**的部位？
2. **向券商確認該帳戶目前的真實期貨部位**。
3. 若真實部位不是系統預期：
   - 需要出清：用「緊急平倉」對真實部位重新查詢並確認平倉；或向券商人工平倉。
   - 需要讓系統重新對齊：關閉程式再重開，讓復原程序以券商實況重新建立基準
     （復原結果需為乾淨才會解除封鎖）。
4. 在真實部位與系統一致前，不要仰賴自動交易。

## 6. 04:55 仍有未平部位

**你會看到**：接近或已過 04:55（Asia/Taipei）仍有部位；或程式在 04:55 前後才啟動／剛從
斷線恢復。

**軟體已自動**：
- 風控（`RiskSupervisor`）在時鐘進入 `[04:55, 10:45)` 時，對有部位的契約**邊緣觸發**
  一次收盤平倉工作流程（`EodFlattenWorkflow`，`SCHEDULED`）：查詢實際淨部位 →
  送出一張數量等於實際部位的平倉單 → 重新查詢，必須精確為 0、無活動／未知委託、
  session 與行情皆健康，才會標記完成。
- **啟動時不會**因為「現在已過 04:55」就自動平倉——只在執行中跨越該時點才觸發，
  避免用陳舊資料盲目平倉。
- 任一步驟失敗會把該工作流程標為 `PAUSED_SAFE`（工作流程層級），不再自動推進。

**你必須**：
1. 若程式在 04:55 之後才啟動而仍有部位：**立即用「緊急平倉」**重新查詢並確認平倉，
   或向券商人工平倉。不要等下一個 04:55。
2. 若收盤平倉工作流程顯示 `PAUSED_SAFE` 或未完成：用「緊急平倉」處理剩餘部位，
   並向券商確認最終部位為 0。
3. 保留當日日誌與 audit 供事後檢視。

## 7. 緊急平倉（手動）

**操作**：
1. 「緊急平倉」區按「緊急平倉（重新查詢）」——系統查詢券商目前的淨部位並顯示。
2. 核對顯示的部位是否合理（必要時同時向券商確認）。
3. 按「確認緊急平倉」——送出一張數量等於查得部位的平倉單，並在成交後重新查詢確認為 0。
4. 若在你按確認前部位又有變動，系統會提示「持倉自上次查詢後已變動，請按『緊急平倉』
   重新查詢後再次確認」——重新查詢後再確認。

**注意**：緊急平倉只平倉、不反手。完成後請確認交易活動區與券商端部位皆為 0。

## 8. 任何未預期例外

- 任何未捕捉例外會被導向安全暫停嘗試並以 `uncaught_exception` / `CRITICAL` 記錄
  （含堆疊）。若無法轉入暫停（狀態機非 RUNNING），程式仍會記錄後結束。
- audit 事件無法寫入（critical）時會嘗試安全暫停並以
  `critical_audit_persistence_failed_safe_pause` 記錄。
- 處置：關閉程式、保存 `%LOCALAPPDATA%\tfx_quant\logs\` 整個目錄、向券商確認部位、
  排除問題後重開讓復原程序重新查得實況。
