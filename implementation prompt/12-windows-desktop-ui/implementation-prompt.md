# Feature 12 — Windows Desktop UI 現代化改造

> **API 文件唯一來源：實作前必須直接讀取專案根目錄 [`交易API元件及說明文件/`](../../交易API元件及說明文件/) 內的元大期貨交易 API 說明、Python 範例、元件與版本資訊。禁止使用 SPARK API 網站、舊 SPARK SDK、舊範例或既有 SPARK 程式碼反推 API；若與本 prompt 其他描述衝突，以該資料夾內文件為準。資料夾缺少、文件未明載或內容矛盾時，須停止相關實作並列為 blocker。市場價格、行情與 OHLCV 不屬於此交易 API 規格，一律使用 `yfinance`。**
> **不得臆測：API 名稱、參數、回傳值、事件、錯誤碼、登入方式、環境、平台、位元數與能力都必須有上述官方文件依據；文件未明載者須標成待確認並隔離於 adapter，不得自行補造。**

> 強制沿用專案既有 Python GUI framework、架構與元件。這是一項既有介面的現代化改造，不是建立另一套 UI；除非現有技術確實無法滿足需求並附上證據，否則不得更換 framework、重寫應用程式或新增平行介面。

## 任務

先完整檢視目前 Windows 桌面介面的畫面、元件、view-model、操作流程、狀態顯示與樣式，再以漸進式修改讓介面更現代、清楚、一致且適合長時間監看。保留所有既有功能、交易語意、application commands、快捷操作與安全保護；不得讓 UI 直接操作元大 API、自行改寫交易狀態，或為了視覺效果改變交易邏輯。

實作前先列出目前 UI 的主要問題及對應改進，包括資訊層級、版面密度、對齊、留白、字體、色彩、元件一致性、操作回饋、錯誤辨識與不同視窗尺寸下的可讀性。依影響程度排序後直接改善，不要只提供設計建議、示意圖或另外新增展示頁。

## 現代化設計要求

- 建立並集中管理設計 token：字體層級、間距、圓角、邊框、陰影、背景、前景、強調色及成功／警告／危險／停用色。不得在各畫面散落互相衝突的 magic values。
- 建立清楚的視覺層級：最重要的環境、連線、策略、持倉與風險狀態必須一眼可見；次要資料分組放入一致的卡片、區段、表格或分頁，避免所有資訊具有相同權重。
- 改善版面與密度：採一致的網格、對齊與留白；充分利用桌面空間但避免擁擠。視窗縮放或常見解析度下不得重疊、截斷重要操作或出現不必要的大面積空白。
- 統一元件外觀與狀態：按鈕、輸入框、下拉選單、表格、分頁、對話框、tooltip、badge 與 scrollbar 應有一致樣式，並完整呈現 normal、hover、focus、pressed、disabled、loading 與 error 狀態。
- 強化互動回饋：耗時操作顯示進度或忙碌狀態並防止重複送出；成功、失敗、阻擋原因及下一步處置要就近且明確呈現，避免只依賴彈窗或日誌。
- 強化資料表格：欄位對齊、數字格式、欄寬、排序、篩選、空狀態與大量資料捲動需易讀；Unknown、Rejected、Partial、斷線、持倉不一致及高風險狀態必須醒目但不造成整頁視覺噪音。
- 支援鍵盤操作、清楚的 focus indicator、合理 tab 順序與足夠色彩對比；顏色不得是傳達狀態的唯一方式。
- 沿用系統可用的繁體中文字型與清晰的數字字型呈現；避免過小文字、過度裝飾、浮誇動畫、玻璃特效或會降低即時交易資訊辨識度的視覺效果。
- 若既有專案已有 theme／style／component 機制，優先擴充與重用；相同用途不得重複建立不同元件。除非專案原本已支援，否則本次不額外加入深色模式。

## 必須保留並改善的資訊與操作

- 全域狀態：環境（模擬／正式）、連線健康、策略狀態、商品、契約月份、元大實際持倉與最後同步時間。
- 控制操作：啟動、暫停、停止、重新查詢、確認同步、緊急平倉。依狀態禁用不合法按鈕；高風險操作須以明確層級呈現具體影響並要求確認，且不可因改版變得更容易誤觸。
- 行情資訊：yfinance 提供且經驗證的最新可用價格／OHLCV、來源 ticker、時間、資料新鮮度、forming 60m K 與最近 closed K；yfinance 未提供的 bid/ask 不得以其他來源補值。
- 策略資訊：紅／黑／十字判斷、連續計數、最後處理 K、允許建倉時間、目前／最近訊號、阻擋原因與加碼設定。
- 委託成交：本地 ID、券商單號、方向、開平、口數、累計成交、狀態、時間及錯誤。
- 損益資訊：每日、每月實際成交毛／淨損益與明細查詢。
- 訊息與處置：錯誤、斷線、持倉不一致、人工處置指引及可搜尋交易紀錄。

可重新分組、調整順序與改善呈現方式，但不得刪除上述內容。若現有介面尚無其中某項，將它整合進現有資訊架構，不得因此另建獨立應用程式或重複整套畫面。

## 行為與安全

UI thread 不得被 API callback、查詢、動畫或大量畫面更新阻塞。視窗關閉、Windows shutdown、最小化、睡眠喚醒需維持既有安全生命週期；有持倉、活動中或未知委託時不得無提示退出。策略暫停與停止的語意要在介面中解釋。任何視覺重構都不得繞過 command enablement、高風險確認、權限、稽核或錯誤處理。

現代化改造應盡量限制在 view、theme、共用元件與必要的 view-model 呈現邏輯。若必須修改 application/domain 層，先說明不可避免的原因，並以測試證明沒有改變交易行為。

## 除錯日誌需求

- 延續記錄畫面生命週期、view-model 狀態更新、command ID、按鈕 enablement 判定與阻擋原因；使用者動作記錄控制名稱、時間與結果，不記錄密碼或輸入欄明文。
- UI dispatcher 記錄排隊深度、更新耗時、跨 thread 拒絕、卡頓門檻及被合併／丟棄的高頻更新數，避免逐 tick INFO log 造成新的 UI 壓力。
- 關閉、shutdown、最小化、睡眠／喚醒與高風險確認須記錄當時持倉／委託摘要、使用者選擇、安全生命週期步驟及失敗後畫面所示處置。
- 不得為純視覺事件加入大量 INFO log；新增的互動與錯誤狀態應沿用現有結構化日誌格式。

## 驗收

- 提供改造前問題與改造後結果的逐項對照，說明實際修改的既有畫面與共用元件；不得以新建 demo、mockup 或未接線頁面代替正式介面。
- 執行既有自動化測試，並用 view-model／UI 測試確認所有 command、按鈕 enablement、狀態顯示、高風險確認與錯誤處理語意未變。
- 測試 100%／125%／150% DPI、常見解析度、視窗縮放、鍵盤導覽、文字截斷、空資料、大量委託／日誌及長時間更新；不得發生版面重疊、重要資訊不可見或明顯卡頓。
- 驗證 normal、hover、focus、pressed、disabled、loading、成功、警告與錯誤狀態的一致性及對比度。
- 依序驗收登入、啟動、訊號、成交、暫停、外部持倉差異、人工同步、緊急平倉與結束程式，確認改造後仍能完成原有操作流程。
- 交付時列出修改檔案、視覺與互動改善、保留的既有行為、測試結果，以及仍存在但未擅自擴張處理的限制。
